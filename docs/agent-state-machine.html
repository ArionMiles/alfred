Run lifecycle

A run pauses rather than terminates when external action can unblock it.

Inside running

Every effectful tool crosses the same executor and policy boundary.

Replay rule: ModelCallCompleted admits ordered output before tools execute. ToolCallRequested or timing/usage records alone do not admit a call. Failed or incomplete streams leave no committed output.

Waiting and continuation

External decisions continue the same run; a new conversation message creates another run.

  • Approval: ResolveApproval records a digest-bound decision before redispatch. Denial becomes a tool error result; approval is evaluated again through policy.
  • AskUser: a tool returns an input prompt. The runner records InputRequested and waits. ProvideInput records the answer, which satisfies that tool call during replay.
  • Interruption: graceful service shutdown stops active writers before marking queued or running executions interrupted. Durable waits and terminal states remain unchanged. Retryable model-stream errors record a safe reason. ResumeRun accepts interrupted runs and uses their original model.
  • Presentation: answer and readable-reasoning deltas are provisional. Clients reconcile completed output and never receive native replay fragments.

Current limits: the default application allows tools without approval prompts. SDK policy can require approval. Service startup does not automatically redispatch unfinished runs, and a crash between an external tool effect and recording its result can leave an effect that replay cannot identify as complete. Cancellation stops execution; it does not undo effects.
